# 评测数据清洗算法设计文档

## 1. 概述

### 1.1 目标

从盲评系统的评测数据中清洗无效数据，为机型排行榜提供可靠的排序依据。

### 1.2 核心原则

- **方向性判断**：排行榜只关心"设备X胜/平/设备Y胜"的方向，不使用原始分值（2分/1分/0.5分）
- **位置映射**：A/B只是图对的展示位置（左/右），不是设备本身。需要通过图对关系查出A/B位置实际对应的设备
- **逐层过滤**：从粗到细，每层过滤掉不同类型的无效数据
- **可追溯**：每条记录的过滤原因可查

### 1.3 位置与设备的关系

**关键概念**：A和B是图对的展示位置（左侧/右侧），不是设备代号。评测对象是IPC（网络摄像头）设备，如TP-Link、海康威视等品牌。

```
图对 pair_1：
  A位置（左侧）→ image_a_id → Image表 → device_id = TP-Link
  B位置（右侧）→ image_b_id → Image表 → device_id = 海康威视

图对 pair_2：
  A位置（左侧）→ image_a_id → Image表 → device_id = 大华
  B位置（右侧）→ image_b_id → Image表 → device_id = 宇视
```

用户选择"A更好"时，实际含义是"左侧图更好"，需要根据图对关系判断是哪个设备胜出。

### 1.4 评分体系说明

**核心原则**：排行榜计算的是设备的累计胜场，不是方向性得分。

| 用户选择 | score_a | score_b | 设备胜负判定 |
|---------|---------|---------|-------------|
| A更好   | 2.0     | 0.0     | A位置设备胜，B位置设备负 |
| A稍好   | 1.0     | 0.0     | A位置设备胜，B位置设备负 |
| 一样好  | 0.5     | 0.5     | 平局，双方各计0.5胜 |
| B稍好   | 0.0     | 1.0     | B位置设备胜，A位置设备负 |
| B更好   | 0.0     | 2.0     | B位置设备胜，A位置设备负 |

**胜场累计逻辑**：
```
用户评分 → 判定胜负 → 查出A/B位置对应设备 → 更新设备胜场

示例：
  pair_1: A位置=TP-Link, B位置=海康威视
  用户选择"A更好" → TP-Link胜(+1), 海康威视负(+0)

  pair_2: A位置=大华, B位置=宇视
  用户选择"B更好" → 宇视胜(+1), 大华负(+0)

  pair_3: A位置=TP-Link, B位置=大华
  用户选择"一样好" → TP-Link(+0.5), 大华(+0.5)
```

**注意**："更好"和"稍好"在排行榜维度上都是"胜"，计1分。强度信息保留在共识强度计算中，但不影响设备胜场累计。

## 2. 评测任务管理流程

### 2.1 轮次机制

```
全局图对池：pair_1, pair_2, pair_3, ..., pair_N

第1轮（所有用户相同）：
  - 45对图对 = 40对新图对 + 10%的重复图对（从本轮40对新图对中随机选）
  - 重复图对在本轮中出现2次
  - 用户共评测 40 + 4 = 44次
  - 用户实际评测的不同图对数：40对
  - 重复图对用于计算重测信度

第2轮（所有用户相同）：
  - 45对图对 = 40对新图对 + 10%的重复图对（从本轮40对新图对中随机选）
  - 重复图对仅来自本轮的新图对，不跨轮次

后续轮次以此类推...
```

### 2.2 数据示例

```
第1轮图对分配：
  新图对：pair_1 ~ pair_40（共40对）
  重复图对：从pair_1~40中随机选4对，比如 pair_37, pair_38, pair_39, pair_40

  用户实际评测序列（44次）：
    pair_1, pair_2, ..., pair_36  （各1次，共35次）
    pair_37, pair_38, pair_39, pair_40  （各2次，共10次）

  用户实际评测次数：36 + 8 = 44次
  用户实际评测的不同图对数：40对
```

### 2.3 关键字段

每条评测记录包含：
- `user_id`：评测用户ID
- `pair_id`：图对ID
- `session_id`：会话ID
- `score`：评分选项（a_much/a_slight/same/b_slight/b_much）
- `score_a`：A得分（新算法不用）
- `score_b`：B得分（新算法不用）
- `is_repeat`：是否重复图对
- `status`：draft/submitted
- `submitted_at`：提交时间

## 3. 状态机

### 3.1 评测记录状态

```
                    ┌─────────────────────────────┐
                    │                             │
                    ▼                             │
    ┌──────────┐  提交  ┌──────────┐  清洗通过  ┌──────────┐
    │  draft   │ ─────→ │ submitted│ ─────────→ │  valid   │
    └──────────┘        └──────────┘            └──────────┘
                             │                      │
                             │ 清洗失败              │ 清洗失败
                             ▼                      ▼
                        ┌──────────┐           ┌──────────┐
                        │ rejected │           │ rejected │
                        └──────────┘           └──────────┘

状态说明：
- draft：用户正在评测，未提交（数据库已有此状态）
- submitted：已提交，等待清洗验证（数据库已有此状态）
- valid：通过清洗，可用于排名计算（需新增）
- rejected：未通过清洗，不参与排名（需新增）

**数据库变更**：evaluations表的status字段需扩展枚举值，新增valid和rejected
```

### 3.2 用户状态（按轮次）

**关键**：用户状态是**按轮次**独立判定的。同一用户在不同轮次中可能有不同的状态。

```
用户A的状态示例：
  第1轮：因时间紧迫快速评测 → 未通过第一层（会话速度异常）→ 本轮状态=invalid
  第2轮：正常评测 → 通过第一层和第二层 → 本轮状态=valid

  结果：第1轮数据不参与排名，第2轮数据参与排名
```

```
单轮状态流转：

    ┌──────────┐  完成本轮评测  ┌──────────┐  第一层通过  ┌──────────┐
    │ inactive │ ─────────────→ │ pending  │ ──────────→ │ tier1_ok │
    └──────────┘                └──────────┘             └──────────┘
                                                              │
                                ┌─────────────────────────────┘
                                │ 第二层通过
                                ▼
                           ┌──────────┐
                           │ valid    │ ← 本轮评测有效，参与排名
                           └──────────┘
                                │
                                │ 清洗失败（任何一层）
                                ▼
                           ┌──────────┐
                           │ invalid  │ ← 本轮评测无效，不参与排名
                           └──────────┘

状态说明：
- inactive：本轮未开始评测
- pending：已完成本轮评测，等待清洗
- tier1_ok：通过第一层（基础质量+重测信度）
- valid：通过全部清洗，本轮数据参与排名
- invalid：未通过清洗，本轮数据不参与排名
```

### 3.3 图对状态

```
正常图对状态流转：

    ┌──────────┐  有效评测>=3  ┌──────────┐  有效评测>=5  ┌──────────┐
    │   new    │ ────────────→ │ evaluating│ ────────────→ │  stable  │
    └──────────┘               └──────────┘               └──────────┘
                                    │                          │
                                    │ 有效评测<3               │ 有效评测<5
                                    ▼                          ▼
                               ┌──────────┐               ┌──────────┐
                               │   new    │               │evaluating│
                               └──────────┘               └──────────┘

状态说明：
- new：刚创建或有效评测数不足，不参与排名
- evaluating：有部分有效评测，但不足以参与排名
- stable：有效评测数充足，参与排名计算
```

## 4. 清洗算法详细流程

### 4.1 第一层：基础数据质量过滤

**设计原则**：尽可能在前端拦截，减少脏数据落库。

#### 4.1.1 子检测1：极速评分过滤

**目的**：过滤观察时间过短的单条记录

**配置**：`MIN_STAY_SECONDS = 1.5`，即1500ms

**说明**：部分待评测图对差异明显，用户可能在1秒内做出判断，因此阈值设为1.5秒。

**前端拦截方案**：
- 0~1.5秒：评分按钮灰色完全禁用，并在合适的地方添加提示，因为1.5秒按钮置灰可能让用户觉得系统卡顿

#### 4.1.2 子检测2：评分无差异

**目的**：过滤所有评测都选同一选项的用户

**规则**：
1. 统计用户所有 valid 记录的评分分布
2. 计算信息熵：`H = -Σ p_i * log2(p_i)`
3. 如果只有一个选项（熵=0），直接 rejected
4. 如果熵 < `ENTROPY_THRESHOLD`（建议1.0），标记为低质量

**前端拦截方案**：
- **单轮提交时检测**：当用户提交本轮评测时，前端检查评分分布
- 如果所有评分都是同一选项，弹出警示：
  ```
  "您本轮所有评测都选择了'一样好'，请确认是否认真观察了图片质量差异？
  如果确认无差异，请点击'确认提交'；如果需要重新评测，请点击'返回修改'"
  ```
- 用户点击"确认提交"后，仍可提交，但后端会标记

**后端处理**：
- 阈值：`ENTROPY_THRESHOLD = 1.0`
- 熵 = 0：用户所有评测都是同一选项，rejected（除非前端已警示并确认）
- 熵 > 0：计算连续的熵惩罚系数
  ```
  entropy_weight = min(1.0, H / ENTROPY_THRESHOLD)
  ```
- 最终权重：`weight = retest_weight × user_agreement × entropy_weight`

**说明**：将熵值直接映射为连续的惩罚系数，避免硬编码0.7的突变。当H=1.0时系数为1，H=0.5时系数为0.5，更平滑自然。

**示例**：
```
用户D的评分分布：
  A更好: 0次
  A稍好: 0次
  一样好: 40次
  B稍好: 0次
  B更好: 0次

  前端警示：用户确认提交
  后端：熵 = 0，rejected，原因：评分无差异（用户已确认）
```

```
用户E的评分分布：
  A更好: 30次
  A稍好: 5次
  一样好: 3次
  B稍好: 2次
  B更好: 0次

  p = [30/40, 5/40, 3/40, 2/40, 0/40]
  H = -(0.75*log2(0.75) + 0.125*log2(0.125) + 0.075*log2(0.075) + 0.05*log2(0.05))
  H ≈ 1.14

  结果：正常，熵 > 1.0
```

#### 4.1.3 子检测3：重测信度

**目的**：通过重复图对验证用户评测的一致性

**数据来源**：本轮中重复出现的图对（约10%）

**算法**：
1. 找出本轮所有重复图对（同一 pair_id 有2条记录）
2. 对每对重复评测，将两次评分映射为设备胜负方向
3. 一致率 = 方向完全一致的对数 / 总重复对数

**阈值**：`RETEST_THRESHOLD = 0.6`

**处理**：
- 一致率 >= 0.6：通过，`retest_weight = 一致率`
- 一致率 < 0.6：**该用户在该轮次的所有评测结果均标记为 rejected**，原因：重测信度不足

**重要说明**：重测信度不通过，意味着该用户本轮的评测不可信，因此本轮所有数据都不参与排名。

**示例**：
```
用户F的第1轮评测（4对重复图对）：

重复图对1（pair_37）：
  第1次评分：A更好 → 方向：A胜
  第2次评分：A稍好 → 方向：A胜
  一致：是

重复图对2（pair_38）：
  第1次评分：一样好 → 方向：平
  第2次评分：B稍好 → 方向：B胜
  一致：否

重复图对3（pair_39）：
  第1次评分：B更好 → 方向：B胜
  第2次评分：B更好 → 方向：B胜
  一致：是

重复图对4（pair_40）：
  第1次评分：A稍好 → 方向：A胜
  第2次评分：一样好 → 方向：平
  一致：否

一致率 = 2/4 = 0.5 < 0.6

结果：rejected，原因：重测信度不足（0.5 < 0.6）
```

```
用户G的第1轮评测（4对重复图对）：

重复图对1：A更好 vs A更好 → 一致
重复图对2：B稍好 vs B稍好 → 一致
重复图对3：一样好 vs A稍好 → 不一致
重复图对4：A更好 vs A更好 → 一致

一致率 = 3/4 = 0.75 >= 0.6

结果：通过，retest_weight = 0.75
```

### 4.2 第二层到第四层的整体流程概述

**目标**：从清洗后的评测数据中，计算出每个机型的0-100综合得分。

```
整体流程：

第一层（基础质量过滤）
  ↓
第二层（用户间一致性验证）→ 筛选出有效用户，计算综合权重
  ↓
第三层（图对共识提取）→ 为每个图对得出设备胜负共识
  ↓
第四层（Bradley-Terry排名）→ 计算各机型的0-100综合得分
```

**关键概念**：
- **第二层**：确保评测者之间有基本共识，剔除"离群"评测者
- **第三层**：将多个用户对同一图对的评测汇总为一个共识结果
- **第四层**：将所有图对的共识结果汇总为各机型的综合得分

---

### 4.3 第二层：用户间一致性验证

**前提**：通过第一层的用户

**目的**：识别与群体共识不一致的评测者

#### 4.3.1 数据准备

1. 取本轮所有通过第一层的有效用户
2. 只使用非重复图对（排除用于重测信度的重复图对）
3. 将评分映射为**设备胜负**：
   - 通过 pair_id 查出 A/B 位置对应的设备
   - "A更好"/"A稍好" → A位置设备胜
   - "一样好" → 平局
   - "B更好"/"B稍好" → B位置设备胜

**直接基于设备判断一致性**：因为同一图对的A/B位置对应的设备对所有用户相同，所以直接比较设备胜负即可，无需通过展示位置中转。

#### 4.3.2 算法（Leave-One-Out组共识）

**优化说明**：原设计需要两两配对计算一致率，复杂度O(U²×P)。采用Leave-One-Out方法，复杂度降为O(U×P)，逻辑更直观。

```
对每个用户u：

步骤1：计算"群体共识方向"
  对u评测的每个图对p：
    收集其他所有有效用户对p的设备胜负判定
    群体共识方向 = 少数服从多数（投票）

步骤2：计算用户与群体共识的一致率
  一致的图对数 = u的设备胜负与群体共识方向相同的图对数
  user_agreement = 一致的图对数 / u评测的图对数
```

**示例**：
```
用户H评测了5个图对，其他有效用户有I、J、K

图对pair_1：
  用户I：TP-Link胜
  用户J：海康威视胜
  用户K：TP-Link胜
  群体共识：TP-Link胜（2票vs1票）

  用户H的判定：TP-Link胜 → 与群体共识一致

对所有5个图对重复上述计算，得出用户H的群体一致率。
```

#### 4.3.3 阈值与处理

**阈值**：`AGREEMENT_THRESHOLD = 0.5`（低于随机水平）

**最小有效用户数**：`MIN_VALID_USERS = 3`

**处理**：
- 有效用户数 < 3：跳过第二层判废逻辑，所有用户标记为"待定"（样本量太小，无法判断）
- 有效用户数 >= 3 且 群体一致率 >= 0.5：通过
- 有效用户数 >= 3 且 群体一致率 < 0.5：rejected，原因：群体一致性不足

**说明**：当样本量极小时（如只有2人），真理不一定在多数人手里。增加最小有效用户数判定，避免极端场景下的"死锁"问题。

#### 4.3.4 示例

```
第1轮有效用户：用户H、用户I、用户J、用户K
非重复图对：pair_1 ~ pair_40（假设前5对如下）

图对设备映射：
  pair_1: A=TP-Link, B=海康威视
  pair_2: A=大华, B=宇视
  pair_3: A=TP-Link, B=大华
  pair_4: A=海康威视, B=宇视
  pair_5: A=TP-Link, B=宇视

用户评分与设备胜负：
  用户H：
    pair_1: A更好 → TP-Link胜
    pair_2: 一样好 → 平局
    pair_3: B更好 → 大华胜
    pair_4: A更好 → 海康威视胜
    pair_5: 一样好 → 平局

  用户I：
    pair_1: A更好 → TP-Link胜
    pair_2: A更好 → 大华胜
    pair_3: B更好 → 大华胜
    pair_4: 一样好 → 平局
    pair_5: 一样好 → 平局

  用户J：
    pair_1: B更好 → 海康威视胜
    pair_2: 一样好 → 平局
    pair_3: A更好 → TP-Link胜
    pair_4: A更好 → 海康威视胜
    pair_5: 一样好 → 平局

  用户K：
    pair_1: A更好 → TP-Link胜
    pair_2: 一样好 → 平局
    pair_3: B更好 → 大华胜
    pair_4: A更好 → 海康威视胜
    pair_5: A更好 → TP-Link胜

计算用户H的一致率（设备胜负比较）：
  vs I:
    pair_1: H=TP-Link胜, I=TP-Link胜 → 一致
    pair_2: H=平局, I=大华胜 → 不一致
    pair_3: H=大华胜, I=大华胜 → 一致
    pair_4: H=海康威视胜, I=平局 → 不一致
    pair_5: H=平局, I=平局 → 一致
    一致率 = 3/5 = 0.6

  vs J:
    pair_1: H=TP-Link胜, J=海康威视胜 → 不一致
    pair_2: H=平局, J=平局 → 一致
    pair_3: H=大华胜, J=TP-Link胜 → 不一致
    pair_4: H=海康威视胜, J=海康威视胜 → 一致
    pair_5: H=平局, J=平局 → 一致
    一致率 = 3/5 = 0.6

  vs K:
    pair_1: H=TP-Link胜, K=TP-Link胜 → 一致
    pair_2: H=平局, K=平局 → 一致
    pair_3: H=大华胜, K=大华胜 → 一致
    pair_4: H=海康威视胜, K=海康威视胜 → 一致
    pair_5: H=平局, K=TP-Link胜 → 不一致
    一致率 = 4/5 = 0.8

  用户H的群体一致率 = (0.6 + 0.6 + 0.8) / 3 = 0.667

  0.667 >= 0.5 → 用户H通过
```

#### 4.3.5 综合权重计算

通过两层验证的用户，计算综合权重：

```
综合权重 = retest_weight × user_agreement × entropy_weight

其中：
- retest_weight：重测信度一致率（0.6~1.0）
- user_agreement：群体一致率（0.5~1.0）
- entropy_weight：熵惩罚系数（0~1.0）
  - entropy_weight = min(1.0, H / ENTROPY_THRESHOLD)
  - H为评分分布的信息熵
  - ENTROPY_THRESHOLD = 1.0
```

**示例**：
```
用户G：
  retest_weight = 0.75
  user_agreement = 0.65
  H = 1.2 → entropy_weight = min(1.0, 1.2/1.0) = 1.0

  综合权重 = 0.75 × 0.65 × 1.0 = 0.4875

用户H：
  retest_weight = 0.8
  user_agreement = 0.7
  H = 0.6 → entropy_weight = min(1.0, 0.6/1.0) = 0.6

  综合权重 = 0.8 × 0.7 × 0.6 = 0.336
```

### 4.4 第三层：图对共识提取

**目的**：从有效用户的评测中，为每个图对提取"共识判断"

#### 4.4.1 数据准备

1. 只处理非重复图对
2. 收集所有有效用户对该图对的评分
3. **查出该图对A/B位置对应的设备ID**
4. 将每个用户的评分直接映射为**设备胜负**：
   - "A更好"/"A稍好" → A位置设备胜
   - "一样好" → 平局
   - "B更好"/"B稍好" → B位置设备胜

#### 4.4.2 加权投票算法

对每个图对 (pair_id, device_A, device_B)：

```
# 步骤1：统计设备A和设备B的加权胜场
device_A_wins = Σ (user_weight × 1)  # 评分判定A位置设备胜的用户权重之和
device_B_wins = Σ (user_weight × 1)  # 评分判定B位置设备胜的用户权重之和
device_ties = Σ (user_weight × 0.5)  # 评分判定平局的用户权重之和（双方各计0.5）

# 步骤2：计算各设备的加权总分
device_A_score = device_A_wins + device_ties
device_B_score = device_B_wins + device_ties

# 步骤3：确定共识胜负
if device_A_score > device_B_score:
    winner = device_A, loser = device_B
elif device_B_score > device_A_score:
    winner = device_B, loser = device_A
else:
    平局，无胜负

# 步骤4：计算共识强度
total_weight = Σ user_weight
score_diff = |device_A_score - device_B_score|
共识强度 = score_diff / total_weight
  - 范围：[0, 1]
  - 越接近1，共识越强
```

#### 4.4.3 示例

```
图对 pair_1：
  A位置（左侧）→ device_id = TP-Link
  B位置（右侧）→ device_id = 海康威视

有效用户评测：
  用户G：A更好 → TP-Link胜, weight=0.4875
  用户H：A稍好 → TP-Link胜, weight=0.28
  用户I：一样好 → 平局, weight=0.55
  用户J：B稍好 → 海康威视胜, weight=0.42

计算设备加权胜场：
  TP-Link胜场 = 0.4875 + 0.28 = 0.7675
  海康威视胜场 = 0.42
  平局加权 = 0.55 × 0.5 = 0.275（双方各计0.275）

设备加权总分：
  TP-Link = 0.7675 + 0.275 = 1.0425
  海康威视 = 0.42 + 0.275 = 0.695

total_weight = 0.4875 + 0.28 + 0.55 + 0.42 = 1.7375
score_diff = |1.0425 - 0.695| = 0.3475

共识胜负：TP-Link（1.0425 > 0.695）
共识强度 = 0.3475 / 1.7375 = 0.2

输出：(pair_1, TP-Link, 海康威视, TP-Link胜, 0.2)
解读：TP-Link略胜海康威视，但共识强度较低（0.2），说明用户分歧较大
```


### 4.5 第四层：Bradley-Terry 排名

#### 4.5.1 胜负矩阵构建

从第三层的共识结果，构建模型间的胜负统计：

**注意**：第三层输出的是实际设备的胜负（如"华为胜"），不是展示位置（A胜/B胜）。

```
对每条共识结果 (pair_id, winner, loser, strength)：

# winner和loser是实际的设备ID
wins[winner][loser] += strength
comparisons[winner][loser] += 1

如果平局（无winner/loser）：
    对于该图对的两个设备 model_X, model_Y：
    wins[model_X][model_Y] += 0.5 × strength
    wins[model_Y][model_X] += 0.5 × strength
    comparisons[model_X][model_Y] += 1
    comparisons[model_Y][model_X] += 1
```

#### 4.5.2 示例

```
假设4个IPC设备：TP-Link、海康威视、大华、宇视

第三层共识结果（已是设备胜负）：
  pair_1: TP-Link胜海康威视, 强度0.2
  pair_2: 宇视胜大华, 强度1.0
  pair_3: TP-Link胜大华, 强度0.206
  pair_4: TP-Link胜宇视, 强度0.6
  pair_5: 海康威视胜宇视, 强度0.4

胜负矩阵构建过程：
  pair_1: wins[TP-Link][海康威视] += 0.2
  pair_2: wins[宇视][大华] += 1.0
  pair_3: wins[TP-Link][大华] += 0.206
  pair_4: wins[TP-Link][宇视] += 0.6
  pair_5: wins[海康威视][宇视] += 0.4

最终胜负矩阵：
             TP-Link  海康威视  大华    宇视
TP-Link        -       0.2     0.206   0.6
海康威视      0.0       -       0.0     0.4
大华          0.0      0.0       -      0.0
宇视          0.0      0.0     1.0       -

解读：
  - TP-Link：赢了海康威视(0.2)、大华(0.206)和宇视(0.6)
  - 海康威视：赢了宇视(0.4)，没赢过TP-Link和大华
  - 大华：没赢过任何人
  - 宇视：赢了大华(1.0)，没赢过TP-Link和海康威视
```

#### 4.5.3 Bradley-Terry 求解（MM算法）

**模型**：假设每个模型有实力参数 π_k，模型 i 击败模型 j 的概率为：
```
P(i > j) = π_i / (π_i + π_j)
```

**MM迭代算法**：
```
初始化：π_k = 1/K（所有模型相等）

迭代直到收敛：
    for each model k:
        W_k = Σ_j wins[k][j]  （k的总胜场加权和）
        π_k_new = W_k / Σ_j [comparisons[k][j] / (π_k + π_j)]
    
    归一化：π_k = π_k / Σ π_k
```

**收敛条件**：`max(|π_k_new - π_k|) < 1e-6`

**平局保护逻辑**：

在标准Bradley-Terry模型中，平局的处理有专门的数学扩展（通常引入阈值参数ν）。当前采用各加0.5×strength是工程近似，在"平局极多"的场景下可能导致所有设备的π_k趋同。

**保护措施**：
```
对每个设备k：
  如果k与其他所有设备的胜负矩阵全是平局（无胜无负）：
    π_k = 1/K（保持基准分，防止因迭代出现异常低分）

最终转换为0-100分时：
  score_k = 60 + normalized_k × 40
  最低分保底为60分
```

#### 4.5.4 示例计算

```
使用上面的胜负矩阵，4个IPC设备：TP-Link、海康威视、大华、宇视

初始：π_TP-Link = π_海康威视 = π_大华 = π_宇视 = 0.25

第1次迭代：
  W_TP-Link = wins[TP-Link][海康威视] + wins[TP-Link][大华] + wins[TP-Link][宇视]
            = 0.2 + 0.206 + 0.6 = 1.006

  W_海康威视 = wins[海康威视][TP-Link] + wins[海康威视][大华] + wins[海康威视][宇视]
             = 0.0 + 0.0 + 0.4 = 0.4

  W_大华 = wins[大华][TP-Link] + wins[大华][海康威视] + wins[大华][宇视]
         = 0.0 + 0.0 + 0.0 = 0.0

  W_宇视 = wins[宇视][TP-Link] + wins[宇视][海康威视] + wins[宇视][大华]
         = 0.0 + 0.0 + 1.0 = 1.0

  分母计算（以TP-Link为例）：
  Σ_j [comparisons[TP-Link][j] / (π_TP-Link + π_j)]
  = 1/(0.25+0.25) + 1/(0.25+0.25) + 1/(0.25+0.25)
  = 2 + 2 + 2 = 6

  π_TP-Link_new = 1.006 / 6 = 0.168

  类似计算其他设备...

  归一化后继续迭代...

最终收敛（示例结果）：
  π_TP-Link ≈ 0.38
  π_宇视 ≈ 0.28
  π_海康威视 ≈ 0.20
  π_大华 ≈ 0.14

排行榜：
  第1名：TP-Link（0.38）
  第2名：宇视（0.28）
  第3名：海康威视（0.20）
  第4名：大华（0.14）
```

## 7. 跨轮次与新增处理

### 7.1 累计计算

排行榜基于**所有轮次**的共识结果，不仅是最新一轮。每轮完成后：
1. 本轮共识结果追加到全局共识池
2. 更新各模型的胜负矩阵
3. 重新计算排行榜

### 7.2 新增图对

1. 新增图对加入后续轮次的图对池
2. 完成评测后进入共识提取流程
3. 有效评测数达到阈值后参与排名

### 7.3 新增用户

1. 从第1轮开始评测
2. 走完整的清洗流程
3. 通过后其评测数据纳入排名计算

### 7.4 排行榜更新频率

建议：每日定时批量计算，或管理员手动触发。避免每条新评测都触发重算。

## 8. 排行榜设计

### 8.1 分数计算

**目标**：将Bradley-Terry模型的π_k转换为0-100的综合得分。

#### 8.1.1 总体得分计算

```
# 步骤1：Bradley-Terry求解
π_k = Bradley-Terry模型求解结果（各设备的实力参数）

# 步骤2：归一化到0-1范围
π_max = max(π_k for all k)
π_min = min(π_k for all k)
normalized_k = (π_k - π_min) / (π_max - π_min)

# 步骤3：转换为0-100分
score_k = 60 + normalized_k × 40

说明：
- 最高分设备：score = 100
- 最低分设备：score = 60
- 其他设备：线性插值到60-100之间
- 为什么最低分是60而非0：避免出现"0分"给用户带来负面印象
```

#### 8.1.2 分场景得分计算

```
对每个场景s：
  1. 筛选出该场景下的所有图对
  2. 只使用这些图对的评测数据
  3. 重新运行Bradley-Terry求解
  4. 按上述方法转换为0-100分

示例：
  TP-Link：
    综合得分：85分
    农村场景：85分
    池塘场景：80分
    公园场景：88分
    城市场景：87分
```

#### 8.1.3 置信度计算

```
对每个设备的得分，计算置信区间：

置信度因子 = min(参与评测的图对数 / 20, 1.0)

置信区间 = ±(1 - 置信度因子) × 10

示例：
  TP-Link：参与评测30对 → 置信度因子 = 1.0 → 置信区间 = ±0分
  大华：参与评测8对 → 置信度因子 = 0.4 → 置信区间 = ±6分
```

### 8.3 特点分析算法

**目的**：自动提取每个机型的优缺点

**算法**：
```
对每个机型M：
  1. 找出M参与的所有图对
  2. 统计M在这些图对中的胜负情况
  3. 分析M胜出/失败的场景特征

优点提取：
  - 在哪些场景下M胜出最多？
  - M胜出时，用户选择"更好"的比例？

缺点提取：
  - 在哪些场景下M失败最多？
  - M失败时，用户选择"更好"的比例？

示例：
  TP-Link：
    胜出场景：农村(15次)、城市(12次)、公园(10次)
    失败场景：池塘(8次)
    优点：夜视清晰、色彩还原自然
    缺点：低光噪点多
```

### 8.4 数据库设计建议

#### 8.4.1 排行榜结果表

```sql
CREATE TABLE ranking_results (
    id INT PRIMARY KEY AUTO_INCREMENT,
    device_id INT NOT NULL,
    scene_id INT NULL,  -- NULL表示综合排名
    score DECIMAL(5,2) NOT NULL,
    rank INT NOT NULL,
    confidence_min DECIMAL(5,2),
    confidence_max DECIMAL(5,2),
    eval_count INT NOT NULL,
    created_at DATETIME DEFAULT CURRENT_TIMESTAMP,
    FOREIGN KEY (device_id) REFERENCES models(id),
    FOREIGN KEY (scene_id) REFERENCES scenes(id)
);
```

#### 8.4.2 机型特点表

```sql
CREATE TABLE model_features (
    id INT PRIMARY KEY AUTO_INCREMENT,
    device_id INT NOT NULL,
    feature_type ENUM('advantage', 'disadvantage'),
    feature_text VARCHAR(500) NOT NULL,
    scene_id INT NULL,  -- NULL表示总体特点
    confidence DECIMAL(3,2),  -- 特点的置信度
    created_at DATETIME DEFAULT CURRENT_TIMESTAMP,
    FOREIGN KEY (device_id) REFERENCES models(id),
    FOREIGN KEY (scene_id) REFERENCES scenes(id)
);
```
