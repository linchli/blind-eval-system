# 数据清洗与排行榜功能设计文档

## 概述

本文档描述将 `clean_and_stats` 模块合并到主后端，并新增排行榜功能的完整设计。

### 核心决策

1. **数据清洗**：完全合并到主后端，service 层代码迁移到 `backend/app/services/`
2. **排行榜缓存**：无 TTL，由数据清洗驱动更新
3. **排行榜入口**：登录页（无需登录）+ 管理侧边栏
4. **得分展示**：双指标（BT 得分 + 评分均值）
5. **筛选方式**：独立筛选（每个条件独立作用）

## 三、数据清洗模块

### 3.1 清洗流程（严格按照 clean_and_stats 算法）

```
管理员点击"执行数据清洗"
         │
         ▼
┌─────────────────────────────────────────────────────────────────┐
│ 第一步：加载数据                                                 │
│                                                                 │
│ 从数据库查询所有 submitted 状态的评测记录：                       │
│ SELECT e.*, ip.scene_id, ip.image_a_id, ip.image_b_id           │
│ FROM evaluations e                                              │
│ JOIN image_pairs ip ON e.pair_id = ip.id                        │
│ WHERE e.status = 'submitted'                                    │
│                                                                 │
│ 结果：得到所有已提交的评测记录列表                                │
│ 每条记录包含：eval_id, user_id, pair_id, scene_id,              │
│               device_a_id, device_b_id, score_a, score_b        │
└─────────────────────────────────────────────────────────────────┘
         │
         ▼
┌─────────────────────────────────────────────────────────────────┐
│ 第二步：单用户一致性检验（重测信度）— 加权 Agreement              │
│                                                                 │
│ 目的：检验每个用户自身的评分是否一致                              │
│                                                                 │
│ 算法（严格按照 clean_and_stats/app/service/cleaner.py）：        │
│                                                                 │
│ 1. 按 user_id 分组，每组独立处理                                │
│    - 验证：所有数据必须为同一用户，否则抛出 NOT_SAME_USER       │
│                                                                 │
│ 2. 分离原始评分和复评数据                                        │
│    - 通过 is_repeat 字段判断：                                   │
│      is_repeat=0 → original（原始评分）                          │
│      is_repeat=1 → retest（复评）                                │
│    - 统计 total_pairs = 唯一 (user_id, pair_id) 组合数          │
│    - retest_count = 唯一的复评 (user_id, pair_id) 组合数        │
│                                                                 │
│ 3. 检查复评比例                                                  │
│    - required_retest = int(total_pairs * 0.10)                  │
│    - retest_count < required_retest → 抛出 NO_RETEST_DATA      │
│                                                                 │
│ 4. 逐场景计算加权 Agreement（scene_weighted_agreement）          │
│    - 将 original 和 retest 按 scene_id 分组                     │
│    - 对每个场景：                                               │
│      a. 按 pair_id 匹配 original 和 retest 记录                 │
│      b. 对每对匹配记录，计算加权一致性得分：                     │
│         - 将原始评分映射为 5 级判定方向：                        │
│           (2,0)→+2, (1,0)→+1, (0.5,0.5)→0, (0,1)→-1, (0,2)→-2│
│         - 查 5×5 加权矩阵得到单对得分：                         │
│           完全一致→+1.0, 偏好减弱→+0.5~0.7,                    │
│           方向翻转→-0.3, 完全反转→-1.0                          │
│      c. 场景级得分 = (mean(单对得分) + 1) / 2 ∈ [0, 1]         │
│                                                                 │
│ 5. 逐场景判定                                                    │
│    - matched_pairs == 0 → rejected                              │
│    - agreement_score >= threshold(0.70) → not rejected           │
│    - agreement_score < hard_reject(0.55) → rejected             │
│    - agreement_score ∈ [0.55, 0.70) → rejected（当前实现）      │
│                                                                 │
│ 6. 标记无效记录（对应 cleaner.py 第 184-196 行）                │
│    - invalid_scenes = 一致性得分低于阈值的场景集合               │
│    - 遍历所有记录：                                             │
│      if scene_id in invalid_scenes AND is_repeat=1:             │
│        → 标记为无效（reject_reason=SINGLE_USER_CONSISTENCY）    │
│      else:                                                      │
│        → 标记为有效                                             │
│    - 即：被拒绝场景中的首次评测记录（is_repeat=0）仍然有效      │
│      只有复评记录（is_repeat=1）被标记无效                      │
└─────────────────────────────────────────────────────────────────┘
         │
         ▼
┌─────────────────────────────────────────────────────────────────┐
│ 第三步：用户组一致性检验 — log-BT Pearson r                      │
│                                                                 │
│ 目的：检验每个用户的评分是否与组共识一致                          │
│                                                                 │
│ 算法（严格按照 clean_and_stats/app/service/cleaner.py）：        │
│                                                                 │
│ 1. 剔除复评数据                                                  │
│    - 按 (user_id, pair_id) 分组                                 │
│    - 每组仅保留 eval_id 最小的记录（首次评测）                   │
│                                                                 │
│ 2. 评分归一化                                                    │
│    - score > 1.0 → 1.0（统一映射 2.0→1.0）                     │
│                                                                 │
│ 3. 按 scene 分组                                                 │
│    - 构建 all_by_scene: {scene_id: [records]}                   │
│    - 构建 user_scene_index: {(user_id, scene_id): [records]}   │
│                                                                 │
│ 4. 计算所有 (user_id, scene_id) 的 log-BT Pearson r             │
│    对每个 (user_id, scene_id)：                                  │
│    a. 计算该用户在该场景的 BT 强度（bradley_terry）              │
│    b. 计算其余用户在该场景的 BT 强度（排除该用户）               │
│    c. 取两者共同的 device_id 集合                                │
│    d. 若共同 device 数 < MIN_DEVICES_PER_SCENE(2) → r=0.0      │
│    e. 对 BT 强度取自然对数：x = log(max(bt[m], 1e-12))         │
│    f. 计算两组 log-BT 向量的 Pearson 相关系数 r                 │
│                                                                 │
│ 5. 计算逐场景动态阈值                                            │
│    - 对每个 scene，收集该场景下所有 (user, scene) 的 r 值        │
│    - threshold = min(mean(r) - std(r), max_threshold(0.85))     │
│                                                                 │
│ 6. 判定                                                          │
│    - r < threshold → 该用户在该场景的所有记录标记为无效          │
│    - r >= threshold → 通过                                       │
│                                                                 │
│ 7. 计算有效数据的 BT 强度（用于排行榜）                          │
│    - 对每个 scene，基于 valid_records 计算 BT 强度               │
└─────────────────────────────────────────────────────────────────┘
         │
         ▼
┌─────────────────────────────────────────────────────────────────┐
│ 第四步：计算排行榜数据                                           │
│                                                                 │
│ 基于清洗后的有效数据（valid_records）：                          │
│                                                                 │
│ 1. BT 得分（Bradley-Terry 强度）                                │
│    - 对所有有效数据运行 BT 模型                                  │
│    - 得到每个 device_id 的强度值                                 │
│    - 归一化到 0-100 分                                          │
│                                                                 │
│ 2. 评分均值                                                     │
│    - 对每个 device，计算所有有效评分的均值                       │
│    - 归一化到 0-100 分                                          │
│                                                                 │
│ 3. 分场景得分                                                   │
│    - 对每个 scene，单独计算 BT 得分和均值                       │
└─────────────────────────────────────────────────────────────────┘
         │
         ▼
┌─────────────────────────────────────────────────────────────────┐
│ 第五步：更新缓存 + 返回结果                                     │
│                                                                 │
│ 1. 将排行榜数据存入内存缓存（Python dict）                      │
│ 2. 记录清洗时间戳和数据快照信息                                  │
│ 3. 返回清洗结果给管理员                                         │
│                                                                 │
│ 从此刻起，排行榜页面访问时直接返回缓存数据                       │
│ 直到下次管理员执行数据清洗                                       │
└─────────────────────────────────────────────────────────────────┘
```

### 3.2 管理员判断是否需要重新清洗

管理员通过以下信息判断是否需要重新清洗：

```
┌─────────────────────────────────────────────────────────────────┐
│  🧹 数据清洗                                    [执行数据清洗]  │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│  清洗状态                                                       │
│  ┌─────────────────────────────────────────────────────────┐   │
│  │ 最后清洗时间：2026-06-09 10:30:00                        │   │
│  │ 清洗时记录数：1500                                      │   │
│  │ 当前记录数：1580                                        │   │
│  │                                                         │   │
│  │ ⚠️ 有 80 条新评测记录，建议重新清洗                      │   │
│  └─────────────────────────────────────────────────────────┘   │
│                                                                 │
│  [执行数据清洗]                                                 │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

判断逻辑：
- 后端记录每次清洗时的 `submitted` 记录总数
- 页面加载时查询当前 `submitted` 记录总数
- 若当前总数 > 清洗时总数 → 显示"有 N 条新评测记录，建议重新清洗"
- 若当前总数 == 清洗时总数 → 显示"数据已是最新"

## 四、排行榜模块

### 4.1 场景结构

系统场景为三层结构：

```
SceneCategory (大类+地点)
  ├── 车库(B4车库)
  │     ├── SceneSubcategory: 白天
  │     │     └── Scene: 车库(B4车库)-白天
  │     ├── SceneSubcategory: 低照
  │     │     └── Scene: 车库(B4车库)-低照
  │     └── ...
  ├── 公园树荫(32楼花园)
  │     └── ...
  └── ...
```

场景命名格式：`{category_name}({location})-{subcategory_name}`

### 4.2 筛选维度

| 筛选类型      | filter_type    | filter_value 示例        | 说明                         |
|--------------|----------------|--------------------------|------------------------------|
| 综合得分      | overall        | null                     | 所有场景的 BT 得分综合        |
| 按大类        | category       | "车库"                   | 包含该大类所有地点的所有子类  |
| 按地点        | location       | "B4车库"                 | 包含该地点的所有子类          |
| 按子类        | subcategory    | "白天"                   | 包含所有大类的该子类场景      |
| 按具体场景    | scene          | "车库(B4车库)-白天"      | 单个场景                     |
| 按主芯片      | chip           | "Hi3516EV300"            | 设备参数筛选                  |
| 按Sensor      | sensor         | "IMX307"                 | 设备参数筛选                  |
| 按焦距        | focal_length   | "4mm"                    | 设备参数筛选                  |
| 按分辨率      | resolution     | "1080P"                  | 设备参数筛选                  |

### 4.3 缓存策略

- **缓存结构**：Python dict，存储完整的排行榜数据
- **更新时机**：管理员执行数据清洗后自动刷新
- **首次访问**：若无缓存，返回空数据 + 提示"请先执行数据清洗"

**说明**：排行榜数据仅在数据清洗时更新，无需手动刷新按钮。清洗完成后排行榜数据即为最新。

### 4.5 API 接口

#### GET /api/leaderboard

获取排行榜数据（无需登录）。

**查询参数**：
- `filter_type`: 筛选类型
- `filter_value`: 筛选值
- `score_type`: 得分类型 (bt | mean)，默认 bt

**响应**：
```json
{
  "code": 0,
  "data": {
    "ranking": [
      {
        "rank": 1,
        "device_id": 5,
        "device_name": "682-A4 1.0",
        "main_chip": "Hi3516EV300",
        "sensor_model": "IMX307",
        "focal_length": "4mm",
        "resolution": "1080P",
        "bt_score": 85.2,
        "mean_score": 82.5,
        "scene_scores": {
          "车库(B4车库)-白天": 88.0,
          "车库(B4车库)-低照": 82.0,
          "公园树荫(32楼花园)-白天": 85.0
        },
        "features": "夜视清晰，色彩还原自然"

    "filter_info": {
      "type": "overall",
      "value": null
    },
    "total_devices": 20,
    "last_updated": "2026-06-09T10:30:00"
  }
}
```

获取可用的筛选选项。

**响应**：
```json
{
  "code": 0,
  "data": {
    "categories": [
      {"id": 1, "name": "车库", "location": "B4车库"},

    "sensors": ["IMX307", "IMX335"],
    "focal_lengths": ["4mm", "6mm"],
    "resolutions": ["1080P", "4K"]
  }
}
```

#### GET /api/leaderboard/details

获取详细评测数据（管理员权限）。

**查询参数**：
- `view_type`: 视图类型 (scene | user | device | pair)
- `id`: 具体 ID（scene_id / user_id / device_id）

**响应（按场景）**：
```json

        "b_win_rate": 0.25,
        "tie_rate": 0.17,
        "bt_a": 1.2,
        "bt_b": 0.8

    ]
  }
}
```
